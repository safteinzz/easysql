# AGENTS.md

Brief for AI coding agent, not people (README is theirs): rules, invariants, gotchas needed to change this project correctly without rediscovering them.

## Hard rules
- **easysql is front end, never client.** No wire protocol, no linked driver, never own store where client has one: writes `~/.pg_service.conf`, `~/.pgpass`, `~/.my.cnf`, hands terminal to real `psql`/`mysql`/`sqlite3`. Keeps `\c`, `.psqlrc`, every script and GUI working; uninstall costs nothing. Feature needing open connection is out of scope, not missing dependency.
- **Never leave user with tool that does not work.** `cargo install easysql` cannot bring clients (not Rust), so handle it. Wherever missing client is found, name *one* command this machine needs (`engines::install_argv` walks PATH for apt-get/pacman/dnf/zypper/apk); TUI offers to run it suspended so sudo and manager can prompt. Three distros of guesses is not help; spawn errno is not error message. Manager or package not known for certain: `package()` returns `None`, name program, never invent package.
- **Password written, never held.** Typed into `Kind::Secret` field, straight into file engine's client reads; never echoed, previewed, logged, put in env var or argv (`ps` shows command line to every user on both machines; why MySQL warns about `-p<password>`). Nothing reads stored password back; UI shows only *that* one exists. **Two exceptions, both hand it over without showing, logging or argv.** SQL Server, only with `mssql_passwords` on (below): client has no password file, so easysql keeps one and hands it over. MySQL under usql, only with `usql_mysql` on: usql driver never reads `~/.my.cnf`, so `mysql::password` takes group's password into one-line passfile usql run holds (`mysql::usql_passfile`), deleted when run ends.
- Tests never touch real `~/.pg_service.conf`, `~/.pgpass`, `~/.my.cnf`, `~/.config/easysql`: use `App::empty()` and `*_in(path, ...)` / `load_from(path)` helpers (temp files, in-memory data).

## Invariants and gotchas
- Connection files: every write through `ini::upsert_as`/`ini::remove`, which change one section, copy every other line byte for byte (comments, blanks, non-UTF-8 bytes, CRLF). Edit in place inside section: key with unchanged meaning keeps its line as written, key not passed loses its line, new key after block's last key, comment between keys stays. Block ends at last key line, so comment or blank above next header, or trailing `!includedir`, never taken by rewrite or delete. Unreadable file is error, never empty file to overwrite. Header read to first `]`, as both clients read it (`[b] # staging`); line break or `]` in name or value refused (would become own lines). `Dialect` says how client reads duplicate key: libpq and our files take first, MySQL last; MySQL value may be quoted and followed by `#` comment (`mysql::option_read`), also how `Dialect::same` decides line unchanged. User's hand-written `connect_timeout` and ordering not ours to reformat.
- **Backups off unless `backups` names count** (`off`, 1, 3, 5, 10): copy per file per save piles up. On: `ini::backup` copies to `~/.local/state/easysql/backups` as `<name>.<epoch>` (leading dot dropped), keeps that many newest per file. Writes never see settings, so answer is process-wide flag set by `ini::set_backups` wherever settings load or change (`main` for every subcommand, `connect`, `App::new`, `apply_settings`); starts off, so test suite leaves no copies. Status lines append `ini::backup_note()`, never hardcoded "backed up". Off is safe because of `ini::write_atomic`, used by every rewrite of user file (`ini`, `.pgpass`, `.psqlrc`): temp file renamed over target, so crash cannot leave truncated `.pgpass`. Follows symlink chain first (also to target not yet existing), renames onto *target* (renaming onto link replaces dotfiles manager's symlink with plain file), copies old mode.
- Section rewrite: keys wizard did not ask about survive via `Section::rest(&KNOWN)`, appended by caller. New wizard field adds its key to engine's `KNOWN` in same edit, else value written twice (as field and as extra).
- `sslmode` (Postgres) and `trust_cert` (SQL Server) are extras wizard *does* own: changed choice replaces key via `engines::set_sslmode`/`set_trust_cert`, index 0 removes key (`SSLMODES[0]` "(unset)" never written as string).
- MySQL: only `[clientNAME]` groups ours. `[client]` read by every MySQL tool, so host there silently redirects `mysqldump` and all else; `name_of` returns `None` for it, `[mysqld]`, and any group whose name after `client` starts with `-` (MariaDB's `[client-server]`, `[client-mariadb]`, read by all its tools). Edit keeps group's existing `password` key: wizard never shows it, rewrite would delete it.
- MySQL password written as mysql reads it (`mysql::option_written`): unquoted, mysql ends value at `#`, trims, reads `\` escapes, so password with any of `#"'\` or edge spaces goes in double quotes, `\` and `"` escaped. `mysql::option_read` reverses it, for usql.
- Blank `.pgpass` match field written `*` (`creds::widen`, in `set_pg_in`, `rekey_pg_in`): libpq always has host, port, user, so empty field matches nothing; password never used, never seen by `covers`.
- `~/.my.cnf`, `~/.esqlpass`, `~/.pgpass`: 0600 from moment temp file exists. `ini::write_atomic` creates those names 0600; `.pgpass` goes through `write_secret_bytes`, since `$PGPASSFILE` can name it anything. Not hygiene: libpq refuses world-readable `.pgpass`, MySQL ignores world-writable `.my.cnf`, file does not work otherwise. Other files keep their mode.
- `.pgpass` is `host:port:database:user:password`, `\` escapes `:` and `\`, `*` wildcard in first four. `set_pg` replaces entry with same first four fields, never appends, and places entry before first line matching every connection it matches (e.g. `*` line for same host): libpq takes first match, line behind it never reached. `Source::Pgpass(i)` counts *entries*, not lines, so comments cannot shift deleted row; delete or move checks entry still has listed four fields (`creds::entry_at`), refuses if file changed underneath. Untouched lines copied as bytes. Connection with no host or default socket dir matches `localhost` line, as libpq (`creds::pgpass_host`).
- `.pgpass` Database defaults to `*` on save: Postgres password belongs to cluster-wide *role*, one secret opens every database there, naming one only makes `\c elsewhere` prompt. Stays editable: behind pooler (pgbouncer, RDS proxy) database name picks backend with other credentials.
- `e` on Passwords moves entry's match fields, keeps secret (`creds::rekey_pg`, by entry index), placed like `set_pg`, refuses move onto another entry's four fields. Password copied line to line, never surfaced, same as every write (rewriting file passes other entries through memory). Invariant: easysql never *shows* stored password, not never touches bytes. Only `.pgpass` has own entries: MySQL password lives in connection's `[clientNAME]`, so `e` there points at connection.
- `o` on Passwords opens `~/.pgpass` or `~/.my.cnf` in `$VISUAL`/`$EDITOR`, suspended like session, after `ini::backup` (copy only when backups on). Exists because libpq takes *first* matching line, so order decides which overlapping entry wins and no wizard field expresses it; backup because editor is only write path easysql does not control. Editor string split on whitespace like client command (`EDITOR="code -w"` works). `refresh_all` after run re-reads file.
- Snippets: plain `.sql` in `~/.config/easysql/snippets`, run as `esql <conn> :<name>` with engine's flag (`Engine::query_flag`: `-c`, `-e`, `-Q`, `None` for sqlite3, which takes query as bare argument). `:` sigil is psql's, cannot collide with client flag or database name, so distinct from bare word meaning ad-hoc SQL. Deliberately not engine-scoped: Postgres-only query fails on MySQL, server's error beats any dialect guess.
- `snippets::sync_psqlrc` regenerates marked block in `~/.psqlrc` (`\set name '…'`) so psql expands `:name` at own prompt; psql only client with variables, so other three get shortcut at shell only. Called from `refresh_snippets`, so every reload (startup, `r`, save, delete, return from `o`) syncs; writes nothing when content unchanged, since it runs on way into every session and would otherwise rewrite file (and back it up) every connect. Flattening strips `--` comments (would swallow rest of one-line value), never inside string, quoted identifier, `$tag$` body or `/* */` block (nests, as server reads it). Only names psql takes as variable (`snippets::psql_name`: letters, digits, `_`, non-ASCII) get `\set` or `:name` in hint; others still run as `esql <conn> :name`.
- `run_suspended` catches SIGINT, SIGQUIT with do-nothing `signal-hook` handler while child runs (`swallow_interrupts`; `Swallowed` guard held until child exits). Registered handler cannot be removed, so registered once with `register_conditional_default`, acts as uncaught whenever no guard alive; unregistering would leave `kill -INT` doing nothing. Ctrl-C goes to whole foreground group: without it Ctrl-C in psql kills easysql mid-suspend, shell left in raw mode. Caught handler, never `SIG_IGN`: ignored signal survives exec, client uncancellable; caught one resets to default in child, so no `pre_exec`, no `unsafe`.
- `hints` setting prints one orientation line before handing over terminal, from `Engine::hint()`, wrapped by `engines::hint_line`, which appends machine's `:names` only when *configured* client really is psql (same gate as install offer): `psql_command` pointed at pgcli reads neither `~/.psqlrc` nor `\set`, so `:name` there is syntax error. Decision in `hint_line_from`, apart from disk-reading `snippets::list()`, testable without real config dir. Only when opening session, never for `esql <conn> :snippet` or `esql <conn> -c '...'`: one-shot prints own result, hint is noise in pipe. TUI prints it *after* alt-screen gone, else wiped with it.
- New tab: `View` variant, its `title()`, state field, `*_rows()`, arms in `render`, `input`, `detail`, `move_sel`. Tab strip built from `VIEWS` via `View::title()` on purpose: second hardcoded list drifts, every tab after new one renders under previous one's name. **Every tape counts `Tab` presses**, so new view between existing ones silently re-aims every later screenshot.
- Identify connection by `Conn::key()` (`<slug>:<name>`), never bare name. Two engines may both have `prod`, so history, selection, `reach` keyed on it, and `engines::find_target` refuses ambiguous bare name, never guesses.
- `Conn::connect_argv` single source of what runs. CLI `exec`, TUI suspended run, wizard live preview all go through it, else preview lies about Enter. `connect_argv_db` same argv aimed at other database; only CLI passes `Some`. Form preview reaches it via `Prompt::draft_conn`: `Conn` from fields plus argv-changing choices (`trust_cert`, SQLite `readonly`).
- `esql <name>/<db>` translated per engine, never passed through. psql's `-d` *and* bare positional land in libpq dbname and username slots, demoting `service=NAME` to username, losing host, port, user; `PGDATABASE` loses to service file. Only working form `psql "service=NAME dbname=DB"` (explicit keywords beat service file's), built by `pg::conninfo`, quoting value as libpq does. MySQL takes `--database=`, sqlcmd's `-d` replaced, SQLite refused in `commands/connect.rs` (other file is other connection). `engines::find_target` tries whole string as name before splitting on last `/`, so name containing `/` resolves; whole name *ambiguous* refuses, never splits (split would aim at unrelated `team` on other host). `pg::conninfo` quotes service name and database, else space breaks libpq parse.
- **Read-only read from file, never remembered.** `Conn::read_only()` asks block itself, so hand-written line turns name blue like form-written one; `pg::read_only` compares setting name case-insensitively, reads every Postgres boolean meaning on (`on`, `1`, any prefix of `true` or `yes`), as server does. Postgres keeps it as `default_transaction_read_only=on` in `options`, which libpq sends for every session through that service (psql, pgAdmin, every driver), surviving `esql <name>/<db>` since service still named. `pg::set_read_only` recognises server's three spellings (`-c name=v`, `-cname=v`, `--name=v`), keeps other `options` tokens in order, drops key when empty; wizard calls it only when answer *changed*, so untouched field never respells user's line. Service line alone **not enough**: pgcli reads service file itself, drops `options`, can write. So any non-psql client session also gets `PGOPTIONS` (`Conn::connect_env`, applied by CLI `exec` and TUI `run_suspended`), read by every libpq client; user's exported `PGOPTIONS` kept, ours appended to win. psql left without it on purpose: applies service `options` itself, beating exported `PGOPTIONS=...off`, so adding it only lengthens displayed commands. Detail panel's raw `options` row drops read-only token: blue line says it, repeating pushes command off panel bottom. Every line showing or copying command (`y`, detail panel, form preview) goes through `widgets::with_env`, so pasted line carries `PGOPTIONS`; without it copied `pgcli service=x` writable. SQLite keeps `readonly=yes` in our `sqlite.conf`; `connect_argv` adds `-readonly`, enforced by sqlite3. Flag is sqlite3's, litecli rejects it, so read-only connection whose configured client lacks sqlite3 flags runs sqlite3 itself, decided in `connect_argv` (CLI, TUI, preview, `y` agree), CLI says so on stderr; `.open` on same file in session reopens writable, so detail panel carries caveat for SQLite as for Postgres. Not offered for MySQL: client honours `init-command=SET SESSION TRANSACTION READ ONLY` in `[clientNAME]`, but `mysqldump` reads that group too, dies on `unknown variable 'init-command'`; fix is `[mysqlNAME]` group easysql would then own through rename and delete. SQL Server has no enforcing session setting. **Before every read-only Postgres session or query, easysql asks server** (`pg::check_read_only`: psql, `-w`, `-X`, probe deadline, after tunnel up, before history stamp), refuses (CLI exit 1, TUI alert) when answer `off` or setting refused outright. Service `options` only request; pgbouncer handles it three ways: default refuses connect (`unsupported startup parameter in options`); `options` in `ignore_startup_parameters` drops it *silently*, session can write; `track_extra_parameters = default_transaction_read_only` honours it, session and transaction pooling alike. No answer (no psql, password prompt needed): said on stderr, session proceeds, since refusing on no evidence locks people out of own database. Postgres one is guardrail, detail panel says so: session can `SET` it off; only role granted only `SELECT` is real limit. Shown by colour, never glyph: name turns `READ_ONLY_COLOR` in list, detail line explains colour in same colour (rarer codepoint falls back to wrong char in some fonts). `esql ls -v` writes `(read-only)` in words: line read by scripts and agents.
- Two-answer choice fields (`Read only`, `Certificate`) drawn as chips (`widgets::chip`); `Field::display` returns chips' plain text so box measured against what is drawn.
- Connection form choice fields found by *label* in `submit_prompt` (`Encryption`, `Certificate`, `Read only`): choices per form depend on engine, fixed index reads wrong one. Renaming label silently breaks save (same trap as tunnel form's "Tunnel through"). Edit writes `sslmode`, `trust_cert` only when answer moved off starting one (`prompt::choices_of`), so value with no matching choice never dropped by untouched edit.
- One-shot runs with client that takes it. Each form uses real client's flags (`-c`, `-e`, `-Q`, conninfo `dbname=`), so `engines::speaks_client_flags` checks *configured* command contains that program (`psql`, `/usr/bin/psql`, `docker exec -it db psql` yes; `pgcli` no); if not, `connect.rs` uses default for this run, says so on stderr. Session still opens in `psql_command` (its purpose); only query and `/db` bypass it, refused only when default missing from PATH. Else pgcli answers `esql <conn> 'select 1'` with `No such option '-c'`, reads conninfo as service name.
- After connection name, four shapes, all decided in `commands/connect.rs`: nothing opens session; `:word` runs snippet; word not starting with `-` is SQL for `push_query` (same `Engine::query_flag()` door as snippets); anything else, plus all after `--`, is client's verbatim. Bare word deliberately like `ssh host 'cmd'`. Without it reflex is `echo '…' | esql conn`: opens *session* with pipe on stdin, prints hint into data when stderr merged, exits 0 on failed query (psql non-zero only for script with `ON_ERROR_STOP`).
- `esql --md <name> ...` one of two runs without `exec` (other: usql run holding passfile or service file, must outlive child). Client is child, stdout piped (stdin, stderr stay terminal's, exit code client's), `markdown::render` redraws output; easysql still never parses SQL or talks to server. Goes *before* name: everything after name is client's. `Engine::table_output` gives flags and shape per engine: psql `-q -c '\pset format csv'`, not `--csv` (`~/.psqlrc` runs after flags, its `\pset format` beats `--csv`; `-q` keeps script `SET` tags out of rows); mysql `--batch` (TSV, backslash-escaped); sqlite3 `-csv -header` (beat `~/.sqliterc`). SQL Server refused unless `usql_cli` on (usql `-C`, quotes comma and quote); sqlcmd has no quoted output. Clients print consecutive results with no separator, so field-count change starts new table; same-width results merge. Counts as one-shot for `use_default_client_for_one_shot` even behind passthrough like `-f` (added flags are real client's). Bare session under `--md` refused.
- Management commands (`conn`, `pw`, `tunnel`, `snippet`, `set`) are TUI wizards without terminal; write only through what wizards call: `engines::save`, `set_sslmode`, `set_trust_cert`, `set_read_only` (rewritten only when answer changed), `carry_rename`, `delete_with_keyed`, `creds::set_pg` with `*` database, `vias::set`, `tunnels::open`. Second write path makes CLI and TUI write different blocks. Every changing command prints one `step` line per change on stdout; `-n` prints exactly those, stops, so step only for what real run does (`snippet` checks whether `~/.psqlrc` would change first). Delete calls `can_ask` before first step (no terminal, no `-y`: refuse, print nothing), `confirm_delete` after. Snippet question typed, like TUI gate: file is only copy. `pw set` reads password before printing step, from `--stdin` or crossterm raw-mode prompt echoing nothing, else refuses; step writes `(set)`. Every printed error chain goes through `commands::said`: keeps contexts, I/O cause in words with what to do, never OS error number. `esql ls` prints names as `esql` takes them: `<engine>:<name>` when bare name shared or a command. `COMMANDS` in `commands/mod.rs` lists every subcommand so `conn add` warns connection named like one opens only as `<engine>:<name>`: add new subcommands there.
- `esql --dump <name>[/<db>] [args]` execs engine's dump tool (`Engine::dump_client`: `pg_dump`, `mysqldump`, sqlite3 `.dump`) via `Conn::dump_argv`, aimed at same block client reads; stdout is dump, exit code tool's. Everything after name is tool's, leading `--` dropped, so bare-word-is-SQL rule off: `esql --dump devmy users` names table for mysqldump. SQLite words go inside `.dump` (tables, `--data-only`), file opened `-readonly`, else mistyped path creates empty database. mysqldump gets database positional (`/db`, else group's), omitted when `-A`/`-B` name own. It reads `[clientNAME]` too: MariaDB's prints two harmless stderr lines about group's `database=` being prefix of `--databases`; Oracle MySQL's refuses (`unknown variable 'database=...'`), so on Oracle tools `--dump` fails for any connection with database set; `loose-database=` would work for both, not written today. pg_dump honours service's read-only `options`, so no read-only check. SQL Server refused: sqlcmd ships no dump tool. Not in TUI.
- Failure path: `tui/probe.rs` re-asks server non-interactively (`select 1`, `-w` so nothing prompts, `PGCONNECT_TIMEOUT`/`--connect-timeout`), classifies client's *own literal strings*. Keep strings verbatim; paraphrase turns honest diagnosis into guess. Probe runs only after failed connect, success path free; exceptions asking on way in: read-only Postgres check, usql `--cset` database list.
- `Confirm` is two of seven box kinds, split by `danger` flag: `Confirm::new` gate before irreversible, red, starts **No**; `Confirm::offer` app volunteering fix after client failed, cyan, starts **Yes**. Offered fix opens fixing wizard with every field pre-filled, or is `ConfirmAction::Remedy`: settings to change plus command run with terminal handed over, then event loop does carried `Retry` (open connection, reopen forward, submit form, copy), so one Yes reaches original goal. Failure with no fix is not `Confirm`: alert (`tui::alert`, yellow, dismiss only), where unstartable client lands.
- Reachability: probe only `Engine::networked()` connections; target with unparseable port dropped, never probed on port 0. TCP connect answers "is anything listening", never "can I log in" or "does that database exist"; labels claim no more. Answers carry `reach_gen`; older generation discarded, never repaints moved list.
- Filtering: every `selected_*` goes through `*_rows()` (selection indexes *filtered* rows; raw vec index picks wrong entry once filter hides anything). `filter::matches` filters, never re-ranks (Connections order earned by `history`).
- **Dot true only while nothing moved, so re-probe whenever something did.** `start_probes` runs on `App::new`, `r`, settings change, after adding or editing connection, **after any tunnel up or down** (wizard, `vias::ensure` on way into session, Tunnels tab `enter`/`d`), and **on return from suspended session**. Miss one: connection shows red `down` while Enter works, because forward came up after only probe.
- List order: Connections sorted by `history::rank` (most recently opened first, then never-used alphabetically), so `refresh_conns` must call `sort_conns`, `App::new` must load history *before* first refresh. `set` still accepts old "alphabetical" (and "alpha"), maps to `ConnOrder::Engine`, so existing settings file not silently reordered. `esql ls` keeps fixed order: script output must not depend on yesterday.
- Action that makes something: `goto_view` to its view, select new row (`select_conn`, `select_tunnel`, `select_snippet`). Same on return from session: used connection moves to top, `select_conn` puts cursor back on it, else cursor stays on row number now naming other connection. Assigning `self.view` directly skips filter clearing, can land on tab hiding just-made thing.
- Adding setting: only in `settings.rs` (field, default, `set` arm, `rows()` entry); Settings tab, file, `d` to default, `esql set` pick it up, no UI work. `save_to` rewrites setting's line in place, keeps every other line (comment, key from newer build). Setting running app acts on must also be re-applied in `apply_settings`, else only next launch.
- `package(PackageManager, Engine)` and `tool_package(PackageManager, Tool)` (ssh, wl-clipboard, xclip) exhaustive, no `_ =>`, so new engine or manager is compile error naming every owed cell, not half-wired feature. Keep both enums; unknown `package()` cell is explicit `None`. Detection probes PATH for each manager's program, not `/etc/os-release`: what is installed matters, not distro machine claims.
- Every `package()` and `tool_package()` row names package checked to bring its programs (`psql` and `pg_dump`, `mysql` and `mysqldump`, `sqlite3`, `ssh`, `wl-copy`, `xclip`). Never add manager whose package names you have not looked up.
- Connection needs found before any offer (`offer_missing`), so one Yes fixes all: client, plus ssh when forward must reopen, installed by one command (`install_argv_for`). Only engine's *default* client installed (package of `pgcli` or docker wrapper unknown): missing configured client, usql included, offered as setting put back (`psql_command` to `psql`, `usql_tui` off), default client installed in same offer if also missing. Failed forward says why in `tunnels::Blocked`: no ssh offers install; host ssh never saw offers one interactive `ssh <host> exit` asking about key (*changed* key reported in ssh's words, never offered: accepting is decision); taken local port offers tunnel form on free one (`free_port_after`), filled by form itself when it failed. No `$VISUAL`/`$EDITOR` offers nano or vi; no clipboard helper offers `wl-clipboard` or `xclip` by session; `.pgpass` entry changed under list (`creds::Gone`) re-reads list, never tells user to press `r`. Alert only for what nothing here can run: sqlcmd (no distro packages it), machine with no known package manager. CLI cannot ask, so errors name command (`install it: …`, `move it: esql tunnel up <name> --local <port>`).
- TUI keys beyond shared vocabulary: `Y` yanks URL, `p` saves password, `t` opens tunnel, `o` opens file in `$EDITOR`. `c` on every tab that makes something except Tunnels (forward made with `t` on connection). `↵`: open on Connections, on/off on Tunnels, change on Settings. `d` on Tunnels deletes row behind gate (`ConfirmAction::DeleteTunnel`): stops it, drops its via so connection no longer reopens it. Yes/No gate for deleting connection, password, tunnel (rebuildable from facts elsewhere); typed gate (`tui::typed`) for snippet (`.sql` only copy). Per-view footers (`CONN_KEYS` and siblings in `tui/mod.rs`) built from `tui::widgets` constants by `key_footer`. Help: `HELP` table in `render.rs`, one `(keys, what)` row per key under lowercase heading, keyless row dim note; `render_help` clamps `help_scroll` (only it knows height).
- Action needing value app knows: picker, not text field. New connection's engine, password's connection, tunnel's ssh host all picked; tunnel host field typed OR picked, `Ctrl-o` opens picker (matched by label containing "Tunnel through"; renaming label silently breaks it).

- Connection can *remember* needed forward in `~/.config/easysql/vias`, keyed by `Conn::key()`. File is ours, not client's: libpq validates every keyword in `~/.pg_service.conf`, refuses whole file over unknown one (`psql: error: syntax error in service file`), so `via=` there breaks connection for psql, pgAdmin, every driver. `vias::ensure` called on way into session by *both* CLI and TUI; no-op when `tunnels::carrying_via(via)` finds this forward running (same spec, same ssh host), so second run never digs second tunnel. Never asked by port alone: two connections may remember same local port for different servers; by port, one reports, reuses, stops other's, and query lands on wrong server. Port held by other forward: `ensure` and `esql tunnel up` refuse, name it. Deleting connection deletes its via (`engines::delete_with_keyed`, called by TUI gate and `esql conn rm`), else file fills with dead forwards.

Red blames database for tunnel one keypress from opening; green is dangerous: probe answering on near end of stopped forward answers for whatever holds that port (local Postgres on 5432), going in unwarned lands migration on wrong server. - Tunnel wizard's first field falls back to `vias::default_host` when `tunnel_host` empty: connection's own last hop, else single host every other via uses, else nothing. Never guesses between two bastions, never overwrites setting (named one is meant).
- Rename changes `Conn::key()`, so **everything keyed on it moves in same save**: `engines::carry_rename` moves via, history, kept SQL Server password; wizard and `esql conn edit --rename` call it after save. - `-L` far end resolved *by ssh host*, not us, so `vias::forward_target` (tunnel wizard and `esql tunnel up`) rewrites target to `127.0.0.1` when `sshhosts::is_same_machine` says database is on hop machine. Common case, invisible when wrong: tunnel up, carries nothing (loopback-bound server ignores own LAN address even from itself). Re-resolved on *leaving* ssh-host field (`leave_field`), not only on picker fill, since field typed or picked.
- Tunnel liveness reads `/proc`, shells out to `kill`: Linux-only, macOS/BSD need other check first. Matches `/proc/<pid>/cmdline` against *this* forward's flag, spec, host, not just `/proc/<pid>` existing: state file outlives reboot, recycled pid would read up and be what Enter or `d` kills. ssh runs `BatchMode=yes` (host key or passphrase prompt fails in ssh's words, no unanswerable prompt) and `ExitOnForwardFailure=yes` (unbindable port ends it). `open` checks local port free, waits up to `UP_WITHIN` until ssh holds listening socket on it (`listening`, from `/proc/net/tcp` and pid's fds, so nothing reaches far end to ask), reports ssh's last lines minus known-hosts notice on giving up. `kill` never signals pid no longer running that forward, returns after ssh exits so replacement can bind port; `list` writes state file only when dropping dead entry, re-reading first so tunnel another esql just recorded survives; spawned ssh reaped in background, no zombies in long TUI session. Forward owned by via it carries (`Tunnel::carries`: spec and host), never port, Tunnels tab included. Two connections to one server via one hop can share one forward (`ensure` reuses it), so deleting connection, replacing its forward, `tunnel down --forget` leave running forward `vias::sharing` says another connection rides; plain `tunnel down` names them.
- SQL Server exception to almost everything, twice. **List is ours**, in `~/.config/easysql/mssql.conf`: no file both clients read (`go-sqlcmd` keeps YAML contexts in `~/.sqlcmd/sqlconfig`, ODBC `sqlcmd` from `mssql-tools18` has no config), so `mssql::flags` builds plain `-S host,port -d db -U user`, both builds understand. Comma in `-S host,port`: sqlcmd takes no colon. **By default stores no password**: never `-P` (Microsoft's docs call it insecure), sqlcmd prompts on handed-over terminal, so agent cannot run `esql <mssql> 'select 1'`. `mssql_passwords` setting (off until user turns on) is way out: `p` on SQL Server connection with it off raises offer saying what easysql would do, Yes turns it on and opens password form. Kept passwords in `~/.esqlpass`, one `[name]` per connection, 0600 via `ini`, in home beside `.pgpass` and `.my.cnf` (where people look), deliberately not `~/.config` (synced, committed; dotfiles backup of `~/.config/easysql` would put plaintext passwords in git). `mssql::password` one of two stored-password reads in crate (other `mysql::password`, for usql); refuses file others can read, as libpq with `.pgpass`, so sqlcmd asks. Secret travels in `SQLCMDPASSWORD` via `Conn::secret_env`, applied by CLI `exec`, TUI `run_suspended`, probe; deliberately not `connect_env`, which everything showing or copying command (`y`, detail panel, preview) uses. Keyed on connection name: rename moves it (`mssql::rename_password`, from `engines::carry_rename` with via and history), delete forgets it; Passwords tab lists it whatever setting says, so one kept while on can be seen and forgotten. `Engine::keeps_password(settings)` gate for `p`, password picker, `pw` flag, detail panel; `stores_password()` answers only whether client has own file, never confused with `networked()` (SQL Server yes too).
- `trust_cert` defaults to validating: ODBC driver 18 encrypts and validates by default, silently waiving it weakens user's connection; `-C` is deliberate answer for self-signed dev server.

Engines covered: `usql_mssql`, `usql_sqlite`, `usql_pg`, `usql_mysql` (default on, on, off, off). MySQL becomes `mysql://USER@HOST:PORT/DB` (`mysql::usql_url`; database in path, so `/db` and `--cset` list from `show databases` need no service trick), group password in `mysql:` passfile line; `mysql::password` reads it as mysql does (`option_read`: `#` comment outside quotes dropped, matching quotes dropped, backslash escapes read); empty one not handed over (usql refuses passfile line with empty field: `line 1 has empty field 5`). Session without handed password: usql asks. `Engine::uses_usql` asked in `client_argv`, `connect_argv_db`, `query_flag` (`-c`), `table_output` (`-C`), `speaks_client_flags` (one-shot never swapped back to sqlcmd), `hint_line_from` (`Engine::usql_hint`; `use <db>` omitted, lasts only for pooled connection it ran on), so CLI, TUI, preview, `y` agree. SQL Server becomes `sqlserver://USER@HOST:PORT?database=DB&encrypt=true` (`mssql::usql_url`, user and database percent-encoded): without `encrypt=true` go-mssqldb accepts any cert; `TrustServerCertificate=true` is `trust_cert` answer. SQLite becomes `sqlite3:file:<percent-encoded path>?mode=rw|ro`, only form whose `mode` driver honours (bare path ignores it): `ro` refuses every write, so read-only stays in usql; `rw` refuses missing file where bare path creates empty one. usql tries empty password before asking, never asks under `-c` or `-f` (`password not available`), so session without handed password gets `-W`, one-shot gets stderr line naming `esql pw set` (`mssql::usql_password_note`). Kept password goes in passfile of exactly one line, `sqlserver:HOST:PORT:*:USER:PASS`, 0600 in 0700 `easysql/pass` under `$XDG_RUNTIME_DIR` or state dir, named by `USQLPASS` from `secret_env` (never `connect_env`), deleted when `Secret` drops. One line: usql matches protocol, host, port only, then logs in as line's user whatever URL asked. Format has no escaping, ends line at `#`, trims, refuses empty fields, so `passfile_line` refuses `:`, `#`, line break, trailing space, missing user, and usql asks instead; user's `~/.usqlpass` never written. CLI run holding passfile spawns and waits, not `exec`, catches Ctrl-C with `tui::swallow_interrupts`, drops `Secret` before `process::exit` (runs no destructors). Pager `USQL_PAGER=less` (plus `LESS=-FRS` unless `LESS` set) in `connect_env`, only when neither `USQL_PAGER` (wins) nor `PAGER` set: usql runs it as one program name, never split (`PAGER='less -S'` gives `executable file not found`). usql resolves `~/.usql_history`, `~/.usqlpass` from passwd entry, not `$HOME`, writes history even for `-c`, so throwaway-HOME run sets `USQL_HISTORY`. usql `\c` takes only full URL or name defined at launch, so before SQL Server or MySQL *session* (not one-shot) both launchers run `usql_csets` via `Conn::usql_session`: `select name from sys.databases` / `show databases` through same passfile with `-w -X -A -t` and probe deadline, then one `--cset NAME=URL` per database (makes `\c b2b` work); hint names `\c <db>` only when list came back. ## Overview
- `src/commands/<verb>.rs`: one file per CLI command, each exposes `run`; shared parts (`step`, `fail`, `-n`, `-y`, `--json`, delete question, hidden password prompt) in `mod.rs`.
- `src/engines/` is the seam: `pg.rs`, `mysql.rs`, `sqlite.rs`, `mssql.rs` each know only which file client already reads and which argv it wants; nothing above knows which database it opens.
- `completion` stays quiet after connection word: rest is client's.

`easysql`: Rust CLI and TUI making databases simple, one binary `esql` replacing `psql`, `mysql`, `sqlite3`, `sqlcmd`, password manager, hand-editing their config files. Smart front end, not reimplementation: every action shells out to real client, every file written is one client already reads. Bare `esql` opens ratatui toolbox (Connections, Passwords, Tunnels, Snippets, Settings tabs and wizards); CLI holds same actions for script or agent (`conn`, `pw`, `tunnel`, `snippet`, `set`, `ls --json`) beside connect. Crate `easysql`, binary `esql`, repo `git@gitlab.com:safteinzz/easysql.git`, AGPL-3.0-only.
